# 需求与共识

> 本文档记录项目启动时（2026-09-26）达成的共识，是后续所有设计和验收的依据。
> 修改需求时直接改本文件，并在提交信息里说明原因。

## 1. 目标

用一个真实的小产品熟悉 **RTOS 项目开发的完整过程**，包括多任务架构、IPC、线程安全、
健壮性、配网、OTA、CI、测试，以及过程中会遇到的各类问题。

## 2. 硬件

| 项 | 说明 |
|---|---|
| 主板 | 合宙 ESP32C3-CORE **简约版**（无 USB 转串口芯片，使用芯片内置 USB-Serial-JTAG） |
| 屏幕 | 合宙 Air101-LCD：ST7735S，160×80，SPI，带五向摇杆 |
| 供电 | USB 常供电，桌面摆件，不做低功耗 |

### 已知硬件约束

- **Flash 模式为 DIO**（GPIO12/13 未接 Flash，用于板载 LED D4/D5）。
- **背光脚 GPIO11 默认是 VDD_SPI**，不烧 eFuse 无法控制 → 背光常亮。
  决策：**不烧 eFuse**；夜间用屏幕睡眠（DISPOFF/SLPIN）实现"熄屏"。以后再评估硬件改线。
- 摇杆键 GPIO4（中）、5、8、9、13，低电平有效。
  - GPIO9 是 BOOT 脚，GPIO8 也是 strapping 脚 → 上电/复位时按住按键可能进入下载模式。
  - GPIO13 与板载 LED D5 共用。
  - 具体方向对应哪个 GPIO 各资料不一致，**M1 实测**。
- LCD 显示偏移因批次而异（常见 x=0/y=24 或 x=1/y=26），**M1 实测**。
- Flash 容量：**M0 实测 4MB**（JEDEC ID `0x852016`，普冉 P25Q32）。芯片 ESP32-C3 rev v0.4。

## 3. 技术栈

## 4. 产品：天气时钟 `c3-weather-clock`

### 4.1 页面（160×80 横屏）

1. **时钟**：时间、日期
2. **当前天气**
3. **三天预报**
4. **系统状态**：空闲堆、WiFi RSSI、各任务栈高水位、固件版本

中文显示，使用 LVGL 字库子集。天气图标用 LVGL 内置符号或自绘像素图标（避开和风图标授权问题）。

### 4.2 交互

| 操作 | 行为 |
|---|---|
| 左 / 右 | 翻页 |
| 30 秒无操作 | 自动回到时钟页 |
| 中键短按 | 立即刷新天气 |
| 中键长按 3 秒 | 进入配网模式 |

### 4.3 数据

- 时间：NTP 对时，北京时间（UTC+8），24 小时制。
- 天气：**和风天气**，每 **30 分钟**刷新一次，一个城市。
  - 和风返回 gzip 压缩的 JSON，需要解压。
  - 每个账号有独立的 **API Host**。
  - 城市：配置页输入中文城市名 → 设备调用和风城市搜索接口 → 取第一个匹配 → 在配置页显示解析结果，确认后保存城市 ID。

### 4.4 配网与配置

- **SoftAP + 配置网页**，一页填完：WiFi SSID / 密码、城市、API Key、API Host。
- 配置保存到 **NVS**。**API Key 永远不进代码仓库。**
- 进入配网模式的条件：首次上电（无配置）、连不上 WiFi、长按中键 3 秒。

### 4.5 OTA

- 固件来源：**GitHub Releases**（公开仓库，HTTPS）。
- 触发：开机检查 + 配置网页按钮 + 串口命令。不做定时自动升级。
- 开启**自动回滚**：新固件自检失败则回退到旧版本。
- 状态页显示当前版本号。

### 4.6 工程能力（全部要做）

- WiFi 配网、NVS 持久化
- 多任务架构，任务间用队列 / 事件组通信，线程安全地访问 LVGL
- 健壮性：断网重连、HTTP 超时重试、任务看门狗、core dump
- 日志 + 串口命令行（esp_console）
- OTA
- CI（GitHub Actions）
- 单元测试

## 5. 分工

| 你（开发者） | Claude |
|---|---|
| 系统架构草案（任务、IPC、模块接口），Claude 评审 | 工具链、工程骨架、CI、PC 模拟器、分区表、构建脚本 |
| 实现所有功能代码 | 测试：纯逻辑模块**测试先行**，硬件相关的**事后补** |
| 写踩坑日志 `docs/pitfalls.md` | 评审 PR、答疑（默认先给提示，要了才给完整代码） |
| 人工验收（L3） | 写验收清单、ADR；跑 L1、L2 冒烟测试 |

技术选型（工具链、库、版本）由 Claude 决定并写 ADR；**架构设计归开发者**。
不可逆的硬件操作、需要花钱或注册账号的事，一律先征求开发者同意。

## 6. 流程

- 分支 → PR → CI（固件编译 + L1 测试）→ Claude 评审 → 合并 → 打 tag 发版。
- 每个里程碑开始前先定**验收清单**（`docs/acceptance/`）。
- UI 先在 PC 模拟器里截图确认，再上板。
- **可测试性硬规则**：纯逻辑放在 `components/*_core` 组件里，只依赖标准 C，
  不 include 任何 ESP-IDF / FreeRTOS / LVGL 头文件。硬件和网络通过薄接口注入。

### 测试分层

| 层 | 内容 | 在哪跑 |
|---|---|---|
| L1 | PC 单元测试（`*_core` 组件） | 本机 WSL + 每个 PR 的 CI |
| L2 | 板上冒烟测试：能开机、命令行能响应、能连上 WiFi | 本机（板子插着），合并前跑 |
| L3 | 人工验收：看屏幕、按摇杆、断网断电 | 开发者按清单执行 |
